This document lists every defect found in lwext4 (https://github.com/gkostka/lwext4, Grzegorz Kostka and contributors, BSD licence) while it was used as the ext2 / ext3 / ext4 library of BifrostFM, and every change made to lwext4’s own sources to fix them. Each patch is explained – the defect, how it was shown, the fix – and given as a unified diff against the upstream release it was made on.

  • Part 1 gives the patches, one section each, with its diff.
  • Part 2 lists defects found and verified – by a test, or by reading the code where a test cannot reach them – that are NOT fixed here.
  • Part 3 lists upstream’s open issues that are not lwext4 defects.

The base: release v1.0.0, and what master already has

The copy was taken from upstream’s v1.0.0 release tag (commit 890484c, 2016-02-09). Every diff below is against v1.0.0, and every patch applies to it: each patch’s hunks were checked with git apply --check against a clean v1.0.0 tree, one patch at a time, and all 50 apply.

Upstream’s master branch is 150 commits later (58bcf89, 2022-09-22, the newest). All 112 of those commits that touch the library (src/, include/) were read against these patches, so each patch section says where master stands:

  • fixed in master – a master commit fixes the same defect (named); the patch is not needed on master;
  • partly fixed in master – a master commit fixes part of it, and what is left is said;
  • not fixed in master – master still has the defect, checked in master’s own code.

Each section also says whether its hunks apply to master as they stand (git apply --check), only with fuzz (patch -F2 --dry-run, every hunk placed), or how many hunks fail there and would need adapting, because master’s code has moved.

One more fact about master for anyone taking these into it: master commit b1a34c5 relicensed master’s xattr and extent code as GPL.

Upstream has been quiet: the newest pull request reviewed is #176 (2026-10-16).

How to read the patches

  • Each hunk is unified diff with two lines of context, lwext4’s own paths (a/src/ext4.c, b/src/ext4.c), and the function it is in after the second @@. The upstream line numbers are v1.0.0’s; the changed-side numbers are those of v1.0.0 with only that patch applied.
  • The changed code is marked in the source with its patch number (“BifrostFM patch N”), so grep "BifrostFM patch" over the copy finds every site; the comments in the hunks are the patch’s own.
  • A hunk that carries the changes of two patches is shown once, under the first, and named under the other (“Also this patch’s …”).
  • A few patches build on others, and compile only with them: patches 7 and 8 need the files they add (below); patch 9 matters only once patches 3, 5, 7 or 8 widen the features lwext4 mounts; patch 41 calls patch 38’s recount; patch 45’s revoke cancel looks in patch 51’s revoke tree, and the hunk shown under patch 46 also defines that tree’s functions.
  • Shown means a test showed the defect – a test image made by e2fsprogs (mke2fs, debugfs), the operation run through lwext4, and the result judged by e2fsprogs (e2fsck -fn, debugfs) – failing before the patch and passing after it. By reading means the fault was found and fixed from the code alone, no test being able to reach it.
  • Patch 11 is not in this list: it changed e2fsprogs, not lwext4.

Part 1 – the patches

Patch 1 – out of space while appending to an extent file never returns

Where: src/ext4_fs.c, ext4_fs_append_inode_dblk, the extent branch.

The defect: the result of ext4_extent_get_blocks was not looked at before ext4_assert(*fblock). On a full filesystem the call fails, the block is 0, the assertion fails – and lwext4’s default ext4_assert prints and then loops for ever. Had it returned, the inode’s size would also have been grown for a block never allocated. ext2 and ext3 (no extents) return ENOSPC as they should.

Shown: a 20 MiB file written into a 16 MiB ext4 image spun at 100 % CPU until killed, at 1 and 4 KiB blocks (a debugger showed ext4_fwrite -> ext4_fs_append_inode_dblk). Patched, the write fails with ENOSPC, and images filled to their last block are e2fsck -fn clean.

The fix: the failure is returned before the assertion and before the size is grown. (The same hunk carries patch 36’s change to that assertion.)

Upstream: fixed in master by ab4ac25 (2016-02-18). Its hunk applies to master only with fuzz, and is not needed there.

Patch 2 – a failed write leaves the device’s write-back count raised

Where: src/ext4.c, ext4_fwrite.

The defect: ext4_fwrite starts write-back cache mode near its top, and two failure exits – appending a block fails (ENOSPC), or a block-map initialisation fails – jump past the matching stop. The block device’s cache_write_back count stays one too high for as long as the device object lives, so a later write-back “off” no longer flushes anything.

Shown: in one process, after a write failed for lack of space, an image then formatted with ext4_mkfs reached the disk WITHOUT its root directory (e2fsck: “Root inode is not a directory”), because the formatter’s own write-back “off” no longer flushed its cache. Patched, the format is clean.

The fix: both exits stop write-back mode before they leave.

Patch 3 – metadata_csum_seed is refused

Where: include/ext4_types.h (the superblock struct, the supported set), include/ext4_super.h, and every metadata checksum seed in ext4_balloc.c, ext4_dir.c, ext4_dir_idx.c, ext4_extent.c, ext4_fs.c (two), ext4_ialloc.c, ext4_xattr.c.

The defect: e2fsprogs 1.43 onward sets the incompatible feature metadata_csum_seed (0x2000, which lwext4 names BG_USE_META_CSUM) by default with metadata_csum, so every recent image – current Raspberry Pi OS among them – carries it. lwext4 lists it as unsupported, so the mount fails with ENOTSUP. With the feature, every metadata checksum is seeded from the superblock’s stored s_checksum_seed (offset 0x270) rather than from crc32c of the uuid, and lwext4’s struct had that word inside its padding.

Shown: a Raspberry Pi OS root partition, refused before, mounted with the patch, was browsed and its files read; the ordinary test images stayed e2fsck clean.

The fix: the superblock gains prj_quota_inum and checksum_seed (out of the padding, same size); EXT4_FINCOM_CSUM_SEED joins the supported set; a new ext4_sb_csum_seed() returns the stored seed when the feature is set and crc32c(uuid) otherwise, and replaces the eight seed computations. The journal’s own checksums (the jbd2 superblock’s uuid) are untouched.

Upstream: not fixed in master. 2 of its 12 hunks need adapting to master; the rest apply.

Patch 4 – a refused mount keeps its mount point

Where: src/ext4.c, ext4_mount (every failure exit after the mount point is claimed) and ext4_umount.

The defect: ext4_mount claims a slot – mounted = 1 and the name – before it opens the device and reads the superblock. When a later step fails (not an ext filesystem, a damaged superblock, an unsupported feature) it returns with the slot still claimed. The next ext4_mount of the same name finds the slot and returns EOK at once, opening nothing: every read then fails with EIO, and ext4_umount calls ext4_bcache_cleanup(NULL) and crashes. The block-size-mismatch exit also left the device open and a dynamic cache allocated.

Shown: a zero-filled file mounted twice: the second mount “succeeded” and the unmount crashed with an access violation. Patched, both mounts are refused, and a good image then mounts, lists and unmounts.

The fix: each failure exit gives the mount point back (mounted = 0, the name cleared); the size-mismatch exit also releases the cache and closes the device; ext4_umount refuses (ENODEV) a mount point that is not mounted or has no cache, so a future slip is an error, not a crash.

Upstream: fixed in master by ce13c49. 1 of its 4 hunks fails on master, and it is not needed there.

Where: include/ext4_types.h, include/ext4_dir_idx.h, src/ext4_inode.c (ext4_inode_get_size), src/ext4_dir_idx.c (ext4_dir_hinfo_init, both path arrays, ext4_dir_dx_split_index, ext4_dir_dx_add_entry).
