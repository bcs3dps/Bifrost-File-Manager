BifrostFM is two programs built from this tree: an engine library in C (bifrost_engine.dll) and the Windows program in C# that uses it (BifrostFM.exe). Most of the tree is BifrostFM’s own code; the engine also builds in six open-source projects, each kept in a folder of its own with its own copyright and licence. This file says which is which.

BifrostFM’s own code is copyright B. C. Services and licensed under the GNU General Public License, version 2 or (at your option) any later version (the licence’s text is LICENSE, and again beside the engine as engine\GPL-2.0.txt). Every one of its source files says so in its header. The open-source code keeps the copyright and licence its own files state.

BifrostFM’s own code – B. C. Services, GPL-2.0-or-later

Where What
build.bat The whole build: engine\build_engine.bat, then gui\build_gui.bat with this script’s arguments.
gui\ The program: the main window and its two panes, the copy and conflict windows, the partition and device windows, the filesystem check window, the properties windows, the text, hex and picture viewers and editors, the settings, and the engine’s interface (EngineNative.cs, EngineSession.cs). Built by gui\build_gui.bat.
gui\json\ The structured editor for JSON, INI and Klipper / Moonraker / KlipperScreen configuration files.
gui\lib\ The busy window, the debug log and its viewer.
gui\art\ The program’s icon and its About picture (drawn by tools\MakeIcon.cs).
engine\ (the files at the top of the folder) The engine: bifrost_engine.h is its public interface; bifrost_engine.c and the bfe_*.c / bfe_*.h files are the session, browsing, editing, copying, the FAT and exFAT side over FatFs, the read-only squashfs side over squashfuse, block devices, device access, imaging, compressed images, formatting, checking, resizing and the capacity test. Built by engine\build_engine.bat.
engine\lwext4\src\ext4_inline.c, ext4_casefold.c and their headers in engine\lwext4\include\ Inline-data and case-insensitive (casefold) directory support added to lwext4.
engine\lwext4\unicode\config.h, ext2_fs.h, ext2fs.h, ext2fsP.h Small stand-in headers that let the three Unicode files beside them build inside lwext4.
engine\e2fsprogs\shim\config.h, mingw_missing.c, mingw_missing.h, sys\ioctl.h, sys\resource.h, termios.h What e2fsprogs needs from a Unix system that Windows does not provide, so it builds with MinGW.
engine\compress\lzma_config\config.h liblzma’s build configuration for this engine.
tools\ The tool that draws the icon and the About picture.

Open-source code built into the engine

Where What Copyright and licence
engine\lwext4\ (all but the files named above) lwext4, the ext2 / ext3 / ext4 implementation the engine works through Grzegorz Kostka and its contributors; a BSD licence, stated in each file. BifrostFM’s changes to these files are marked where they are made, with BifrostFM patch N comments.
engine\lwext4\unicode\nls_utf8.c, utf8data.h, utf8n.h UTF-8 normalisation and case folding, taken from e2fsprogs SGI and Collabora; GPL-2.0, as each file states.
engine\e2fsprogs\ (all but the files named above) e2fsprogs 1.47.4: e2fsck, resize2fs and the libraries they use; in shim\, e2fsprogs’ own headers and the files its build generates Theodore Ts’o and its contributors; e2fsck and resize2fs under the GNU GPL, the libraries under the GNU LGPL and, for the UUID library, a BSD licence – as each file states.
engine\compress\xz-5.8.1\ liblzma from XZ Utils 5.8.1 (.xz images, and squashfs “xz” and “lzma” blocks; its BCJ filters read) The XZ Utils authors; 0BSD (COPYING, COPYING.0BSD).
engine\compress\zlib-1.3.1\ zlib 1.3.1 (.gz and .zip images, and squashfs “gzip” blocks) Jean-loup Gailly and Mark Adler; the zlib licence (LICENSE).
engine\squashfuse\ squashfuse 0.6.5’s reader, the squashfs implementation the engine works through (read-only) Dave Vasilevsky (squashfs_fs.h Phillip Lougher’s); BSD 2-clause (LICENSE). Used as released but for decompress.c, which carries BifrostFM squashfuse patch 1 (SQUASHFUSE_UPSTREAM.md).
engine\compress\zstd-1.5.7\ Zstandard 1.5.7 (.zst images, and squashfs “zstd” blocks) Meta Platforms, Inc. and affiliates; BSD or GPL-2.0, at your choice (LICENSE, COPYING).
engine\fatfs\ FatFs R0.16, the FAT12 / FAT16 / FAT32 and exFAT implementation the engine works through ChaN; a 1-clause BSD-style licence (LICENSE.txt), compatible with the GNU GPL. Its configuration, source\ffconf.h, carries BifrostFM’s settings, each marked BifrostFM FatFs patch 1; source\ff.c carries BifrostFM FatFs patch 2 (a volume is looked for at the range’s first sector only, never through a partition table there).

This source release leaves out BifrostFM’s own tests and e2fsprogs’ upstream test data and test programs (lib\blkid\tests\, lib\et\test_cases\, the tst_* programs, test_io.c, scantest.c, test_probe.in, test-resize and test_extent.*); none of them is part of the build.

Folder by folder, file by file

(Being filled in as each file is reviewed: a folder or file not listed here has not been reached yet. This note goes when the list is complete.)

gui\

The Windows program, BifrostFM.exe: C# WinForms, compiled as one 64-bit exe by build_gui.bat into out\ at the top of the tree.

File What it holds, and what for
AboutForm.cs The About window: the program’s name, picture, version, description, features and licence and credit lines, laid out in code from the measured text; modeless, so it can stay open beside the main window.
AppSettings.cs The program’s remembered settings, kept in the registry under HKEY_CURRENT_USER\Software\BifrostFM: the name of every value with its meaning and default, and the four calls that read and write them – a read never fails (a missing or wrong value gives the caller’s default) and a failed write is ignored.
build_gui.bat The program’s build: closes a running copy, steps the version, compiles engine.rc’s resources with windres and every listed source with the .NET Framework’s own csc into one x64 exe in out\, and records the new version only once the exe has compiled; a development build also leaves the engine DLL beside the exe and keeps a debug log on every run.
CheckForm.cs The Check Filesystem window: e2fsck’s report line by line as it arrives (in a fixed-pitch face), a bar over its five passes, the verdict when it finishes – with a note when the filesystem’s journal is on another device – and Copy, Cancel and a Repair, each posted through the main window (the worker asks before it repairs, and runs the check); shown modal over the main window, and it cannot be closed while a run is under way.
CommandArguments.cs The arguments requests carry – an edit’s, a copy’s or cut’s, a save’s, a raw copy’s, a table write’s or format’s, a partition command’s, a restart’s – each copying what it is given so a later change in a window cannot change a queued request; and the one factory every request is made through, which checks each kind’s arguments and shape and builds the duplicate and stream keys the queue compares.
CommandCheckViews.cs How a filesystem check’s window is told about each run – a Begin when it starts and a Finished with its result when it ends – sent by the command worker apart from the request’s own completion, which may go to a callback that consumes the result; one window serves the check and a Repair after it, with a way out when the window cannot be told at all.
CommandClient.cs The UI’s end of the command system: posting requests with their one-shot completions, and bringing the worker’s views onto the UI thread (posted, never called) – each result to its completion, the rest to the main window’s renderer – plus the direct channel a drag-out’s extract uses while the UI thread is held in OLE’s GetData.
CommandClipboard.cs The main window’s clipboard dealings for paste and cut: what a paste uses, read as one snapshot between two equal readings of Windows’ clipboard sequence number; the key that ties copied image items to this run and the image open when they were copied; and, after a cut has been carried out, the clear – made only while the clipboard is held open and only if it still holds that cut.
CommandContracts.cs The shapes the command system’s two sides exchange: the request kinds with their scheduling classes and the worker’s modes, the steps a sequence is built from, the views, questions and answers; the request envelope the UI posts (frozen when posted, values only), a step’s result, the worker’s record of an open editor, the state view the UI mirrors, and the table binding the worker to its native steps.
CommandCopySequence.cs Every copy and cut as one command on the worker – Extract, Import and Copy Within: free ” - Copy” names for a copy pasted beside itself, write access when the image changes, a rename for a cut within the image, the copy under its progress window, and for a cut across filesystems the removal of the sources (deleted from the image, or sent to the Recycle Bin) only after a copy that reported no problem, with both results kept.
CommandDeviceOpening.cs Open Device, and Check Filesystem on a device, as one command sequence on the worker: the device asked for when the menu has not chosen one, its partition table read, the rows that do not fit the device marked invalid (the device refused only when none fits), the partition asked for when there is a table, and the chosen range handed to the ordinary image-open sequence; nothing open is touched until a partition is chosen.
CommandEditorBinding.cs The command worker’s record of the editors open on Windows files: the two sets it keeps (editors that save into the image, which closing the image must deal with, and those that save to a Windows file) and what a finished Save As changes in them – an editor moves between the sets, and its original content stays with it until it closes.
CommandEditorCoordinator.cs The main window’s side of the editors: which editor windows exist and the id each has in the command system, the saves they hand over (an image entry’s as a SaveEditor request carrying a snapshot, a Windows file’s – already written by the editor – as the report of a fact), whether each editor’s image is still open, and the worker’s close questions, shown inside the editor only once its own work and saves have returned and answered from what really happened to the window.
CommandImageOpening.cs Open Image and Check Filesystem on an image file as one command on the worker: the file’s partition table read first with nothing open touched, the partition asked for when there is a table (the length always from the table, never the dialog), the ordinary Open or Check run on the chosen range, and – for a file with no table that will not mount whole – one chance to type the offset, with a note of what the file’s first page holds.
CommandImportControl.cs The engine callback for an editor’s save into the image (one file imported under a temporary name before it replaces the entry): it lets the running command pause or stop the copy before the entry is touched, keeps that file’s own failure where the import says only “partial”, and keeps a failure inside the callback apart from a user’s cancel.
CommandInputs.cs The command system’s inputs – every window that asks the user for values (a Save As target, an image folder, a Windows file, a device, format options, a new file’s name, Properties): the records of what was asked and what was chosen, the worker’s acceptance of an input (with what its window needs read first), its hold on other work while a modal input is open, and its closing of inputs before an editor or the image is closed; and the UI’s registry, which reports each input’s end only once its window has really returned.
CommandInterrupts.cs How a command running on the worker is interrupted and asks the user something: the checkpoint where a Cancel stops it and a pending Exit is asked about first (consent before cancellation), the wait for a question’s answer that watches for Cancel and Exit, and the Exit question that takes a command’s question down and, on a No, puts it back with what had been typed.
CommandLayoutReader.cs The raw reader the partition-table parsers are given when the command system reads a disk’s layout: it keeps the first read failure, with the engine’s detail line, so a failed read is reported instead of coming out of the parsers’ fallbacks as an emptier layout – while a read past the disk’s end (a table naming a place the disk does not have) answers “not there” without failing the layout.
CommandLifetimes.cs The UI thread’s watch over every window the command worker waits on – an input’s picker, the partition and check windows, the editors – so that one that disappears without sending its close notice (its owner unwound with an exception, a disposal failed half-way) still has its owner’s “it has ended” handler called, once, and can never hold the worker for good.
CommandNativeControl.cs The managed side of the engine’s callbacks during a command’s copy or check, on the worker: each event copied out of engine memory at once, counted into the result (items copied, problems, notes), a destination that exists or a manifest-named file asked about (or settled by an earlier “All” answer, or quietly for a drag-out), progress published at a bounded rate, and any managed exception kept as the failure with the engine told to cancel.
CommandNativeOperations.cs The command worker’s native steps for the copies, the raw copy (with the image file’s SHA-256 written beside it), the format, the check (and what an expansion may do after it), the resize and the capacity test, each through its EngineSession.cs helper with the command’s own callbacks; and the read-out of an image file into a stage file of its own for an editor, which this code deletes on every failure and hands, on success, to the opening sequence and the editor.
CommandNativeSteps.cs The command worker’s step runner: one case per sequence step, each handing the captured request to its EngineSession.cs helper (open, close, list, volume facts, link text, disks, image facts, a table write, the edits, a save that asks before replacing) or to a function of its own (the layout and a picker’s partition choices, read so a failed read is reported rather than taken for an empty disk; where a disk’s backup GPT ends; New Image’s file), returning each helper’s own result record; and the release of the stage files a finished request carried.
CommandNavigation.cs Moving the image pane to another folder, and the record of a finished folder listing that the worker hands to a window: the worker’s current folder for the main pane (the one a later change re-lists) moves only once the new folder has been read; the folder pickers’ listings travel in the same record but never move it.
CommandOperations.cs The ordinary operations’ sequences: the dispatcher that sends each request kind to its sequence or runs its one step (an edit first asking for its name or its Delete, then taking write access, then re-listing the pane, a New File then opening in its editor); the opening of an image file in an editor, its viewer chosen – asking about binary or too-large content – before the editor is registered; the plain-text fallback for a structured file that would not load; the partition window’s disk operations with their questions, progress and layout re-read; and the records these hand the UI.
CommandPickerBranch.cs The listings an image folder picker needs to open its tree at a starting folder: the root and every folder down to it, read in turn as one sequence on the worker and handed over together, ending at a folder that cannot be listed with the ones before it kept.
CommandPickerFolder.cs The image Save As dialog’s New Folder, run as one command on the worker: the name asked for and checked, the filesystem made writable if need be, the folder made and committed, and the folder it was made in and the new folder listed back so the dialog shows and enters it – with the request’s payload that binds it to the dialog and its editor’s destination, and the result’s record that the folder was made even when its listings did not finish.
CommandProgressWindows.cs The progress windows a command shows while the worker runs it – the copy progress dialog or the “working” box – opened, updated and closed by the command’s progress views and keyed by its serial: the window’s Cancel posts a Cancel request, a window that cannot be built cancels its command, and a question (or the Exit question) is asked over a live progress window rather than behind it.
CommandQuestionPresenter.cs The window side of the worker’s questions: each question shown over the window it belongs to (looked up from the id it carries – an editor, a picker, a progress, check or partition window, or the main window), in the dialog its kind uses – the Yes / No warnings worded from what the request captured, the binary-file, conflict, metadata-clash, name, offset and partition-write questions, and the dialogs a sequence asks for its own values (the partition window’s format options, partition file, table kind and new partition; New Image’s file and size, its Browse and its Match a Device, which refuses a disk longer than the size box takes; the device an operation works on; Read Device’s device, range and file; Write Device’s and Partition/Format’s image files) – and answered through its own display, Cancel when it cannot be shown; the record of each display’s popups and of the editors’ close questions shown for it, so an Exit can close them; and the draft of a name or offset question, kept across an Exit declined.
CommandQuestions.cs The question a running command asks, as the worker and the windows share it: the question, which outlives any one popup; the display reference each showing gets, which alone may answer while current; the answer; the draft typed into a question, kept so it can be shown again after an Exit is declined; and the services a command’s steps use – ask, check for an interrupt, publish a view.
CommandRawSequence.cs The raw copies as command sequences: Read Device (a whole device, or only through its backup GPT, to an image file) and Write Device (a plain or compressed image to a device, always read back), and the partition window’s Read, Write and Erase of one partition – each checking the captured request, inspecting the image file or the GPT just before acting, asking before anything destructive, and running the copy under its progress window; after a partition write or erase the layout is read again.
CommandRecycleSources.cs The last step of a cut from Windows into the image: once every item has been copied, the Windows originals are sent to the Recycle Bin one at a time through the framework’s Visual Basic file calls (Windows’ own dialog when one cannot be removed), stopping at the first that cannot be removed or is cancelled; the copies in the image stay whatever happens.
CommandSequences.cs The command worker’s gate and its whole sequences: every request held first to the present state (is a filesystem open, which window owns the disk, is it the same open as when asked), then run start to finish – leaving the open filesystem (Close and Continue, each editor asked to save, the session closed), opening one read-only or reopening it writable on the first change, saving an editor, the check and partition windows’ openings and closes (New Image’s file and size, and Partition/Format’s disk or disk image, asked as questions of their own sequence before anything is closed), the risk-warnings option, and Exit or the restart as Administrator.
CommandStage.cs The staged files a command takes its content from (an editor’s save, a new file’s first content): each a file of its own, written whole, flushed to disk and closed before any command gets it, with a token that deletes it exactly once or hands it on; and the background job that writes the hex editor’s save – its file with the changed bytes laid over it – passing the result to the UI through one atomic exchange.
CommandSystem.cs The command system’s core: its one worker thread, which runs each request’s whole sequence before taking the next; the admission of posted requests by their scheduling class (interrupts first, newest-value streams replaced, duplicates dropped, fresh user work refused while busy or exiting); the drag reservation that keeps the worker free while the UI waits inside a drag; the publication of views to the UI; and the end of the queue at Exit.
CopyForms.cs The three windows a copy shows, all modal: the progress dialog (the item or the raw phase being worked on, a bar, and the counts – items, or sectors, MiB or steps for a device copy, a format’s zeros, the image’s SHA-256 and the capacity test – with a Cancel that asks the copy to stop and stays up until it has), the question asked when a destination file already exists (Overwrite, Overwrite All, Skip, Skip All, Cancel), and the question asked when a folder extracted with the metadata manifest holds an entry of the manifest’s own name (keep that entry, keep the manifest, or Cancel).
DebugValues.cs The values that exist only in a DEBUG build, for testing: project-wide globals read and written directly, the whole file and every use of it inside #if DEBUG, each set only from the command line at start-up (Program.cs) or a constant, and never kept in the registry or a file.
DiskLayoutForm.cs The partition window behind File > Partition/Format: the disk drawn as a bar with its partitions coloured by what they hold, the same in a list, and the commands – a new table (MBR, GPT or none), Add and Delete Partition, Make and Expand Filesystem, a partition read to a file, written from one or erased, Write Table (warned), Revert, Refresh, Test Capacity and Open – each press with work posted through the host to the command worker, which asks its questions, makes the edit on a copy of the table and hands it back; nothing reaches the disk until Write Table. With it, the New Table and Add Partition dialogs.
DragData.cs A drag out of the image pane: the data object that offers Windows a file list from the start but extracts the items only when another program actually takes the drop (and never for a drop on this program’s own Windows pane), and the small window, on a thread of its own, that shows that extract’s progress and Cancel.
EditorSaveMenu.cs What the text and hex editors share for Save As: the Save As item made into its two choices (into the image, or to a Windows file), the check a chosen Windows path must pass (a plain file in an existing folder, no device name, never over the image, the editor’s work file or its original, or inside the staging folder), and the question asked when an editor closes while its image is gone – save to Windows, discard, or keep editing.
engine.rc The Win32 resources compiled into the exe: the version Explorer shows, the program icon, the engine DLL itself (so a release build is one file) and the About window’s picture, under the ids EngineNative.cs looks them up by.
EngineNative.cs The program’s side of the engine DLL: finding it (beside the exe, or extracted from inside the exe to a per-run temporary folder), loading and unloading it by hand, binding every engine function to a delegate, the structures and constants mirrored from engine\bifrost_engine.h, and the plain-language sentence for each status code.
EngineSession.cs The program’s calls into the engine, one synchronous function per operation – open and close, list, the edits and an editor’s save, copies, check, resize, format, raw device copies, a partition table’s write and the capacity test – called only by the command worker’s native steps, so every engine call runs on that one thread; the result record each fills; and the check, copy and delete controls whose callbacks the engine calls while an operation runs, handing each event to the command’s own control (the delete’s opening the copy window once it grows large, with Cancel).
EntryIcons.cs The image pane’s own icons – folder, file, symbolic link, device, pipe and the “..” way up – drawn from a few shapes on a 16-unit grid at any size, with no picture files; the folder and page drawings are shared with the toolbar’s pictures.
FsPropertiesForm.cs The Filesystem Properties window: where the open filesystem is (file or device, and its byte range), its type as blkid would name it, label, open mode, journal notes, capacity, used and free (with a bar), block and inode counts, and its feature list exactly as dumpe2fs prints it – read from the engine just before it opens; Copy puts every row on the clipboard.
HexEditForm.cs The program’s own hex editor, for a file in the image or a Windows file: an offset column, sixteen bytes a row in hex and as text, typing that overwrites (never inserts) so a file of any size is shown without holding it in memory; Save, Save As, Go to Offset and a remembered text size.
ImageFolderForm.cs The folder picker for the inside of the open image: a tree of its directories, each listed by the command worker the first time it is opened, which starts expanded down to the folder it is given (one request lists the way down).
ImageSaveForm.cs The Save As dialog for saving an editor’s file into the open image (whatever it was opened from), shaped like the Windows one: a tree of the image’s directories and a list of the entries in the one shown, every listing a request to the command worker bound to that image, with Up, New Folder (asked, made and listed back by the worker) and a name box that also takes a path inside the image or a Windows drive path (which sends the save to Windows), held to FAT’s name rules on a FAT image; it only chooses – the editor’s save writes, and the worker asks before replacing a file.
MainCommand.cs The main window’s side of the command system: its start and its shutdown through the worker’s Exit; the renderers that show what the worker publishes (state, folder listings, opens, editors and viewers, questions, inputs, progress, the check and partition windows); the partition window’s view, which posts its buttons’ requests and holds back questions while its own message boxes are up; the routing of every admitted input to its dialog or picker – file names, devices, Read Device’s choices, Properties, an editor’s Save As target, the Windows-pane actions – with the request each choice becomes posted only after the dialog has gone; and the reports of copies, raw copies, checks and partition work. It runs no engine work itself.
MainForm.cs The main window: the image pane on the left (an image file’s or a device partition’s filesystem – ext2/3/4, squashfs, FAT or exFAT) and the Windows pane on the right, each with its path row, toolbar, five views, sorting and column sizing; the menus and the right-click menus; and the click side of every command – the selection, folder and state captured and posted to the command worker (MainCommand.cs and the Command* files), the only thing that reaches the engine: Extract and Import, drag and drop and the clipboard, New Folder, New File, Rename, Delete and Properties in either pane, Open and Open As, Enable Writing, Open, Read, Write and Partition Device with the restart as Administrator, New Image, Check Filesystem and its Repair. Also the Windows pane’s own reading and its actions (run once the worker admits them), the making of the editors and viewers the worker opens, the hand-over of their saves to the editor coordinator, and the remembered window, panes and options.
make_version.bat The build’s version number: reads version.txt (the last successful build’s MAJOR.MINOR.BUILD), refuses anything but three plain numbers, steps BUILD for a build of the program (or keeps it for a test build), and writes the number for the compiler, for engine.rc, and for version.txt afterwards.
MessageForm.cs The program’s own message box, used everywhere MessageBox.Show would be: the same button sets, icons, sounds, default and cancel buttons and Ctrl+C copy as the Windows box, but in the dialog font the caller passes (the Windows box takes none); plus a variant that opens with a red warning heading for a question that must be read. Self-contained.
NewImageForm.cs Two small dialogs: the one that asks for a new image’s file and exact size (in bytes, sectors, KiB, MiB or GiB, with “Match a Device” to copy a card’s length) for New Image, or for a partition’s filesystem type, block size, label and an optional erase for Make Filesystem, checking every answer before it closes; and the “working” box with a moving bar, which the progress windows show for a command whose progress view asks for it (work with no progress to report).
OpenScan.cs What Open needs before a window appears, and what an editor knows about its file: deciding from a file’s content whether it is text, a picture or binary (known signatures, NUL and control bytes in its first 64 KiB); which structured editor takes it (by name, a printer config’s kind – Klipper, Moonraker, KlipperScreen – by its sections, an unnamed file only if it reads as JSON); the question asked before a binary file is opened; and the descriptor every editor holds (where the file is now, the command facts its saves carry, and where it was opened from).
PaneListView.cs The list control both panes use: a list view that paints double-buffered, reports when the USER resizes a column, lays the List and Small Icons views out on an even grid sized to the widest name (with a name cap, cut names shown whole on hover), and handles item check boxes – a filled box for the “..” row, a select-all box in the heading, and a double-click that opens without toggling a tick. Self-contained.
PaneSorter.cs The order of a pane’s rows: “..” first, folders before files, then the chosen column ascending or descending, with the names breaking ties – sizes compared as numbers, ext4 names case-sensitively and Windows names ignoring case.
PartitionForm.cs Two dialogs for choosing where to open: the partition dialog (a disk image’s or device’s MBR, logical or GPT partitions with what each holds, or a typed byte offset) with the simple table reader that fills it; and the device picker (the physical disks, portable ones by default, with the “how much” row for reading or writing an image), plus the size, model and bus wording other windows share.
PartitionTable.cs A disk’s MBR or GPT partition table as bytes, for the partition window: reading one (keeping every field, boot code and vendor GUIDs included, so it can be written back), the checks a table must pass, building the sectors that write it (protective MBR, both GPT headers and entry copies with their CRC-32s, or an erase) and the erase of an old GPT’s headers the new table leaves, the deep copy the worker edits, the free gaps and new entries the window edits with, the common type names, and a probe of what each partition’s first page holds (ext2/3/4, FAT, exFAT, NTFS, squashfs, swap). It uses nothing else of the program; its reads go through the engine via CommandLayoutReader.cs, its writes via EngineSession.cs.
PictureViewForm.cs The picture viewer: a look-only window for a PNG or JPEG entry of an image, showing it at its real size when it fits and scaled down to fit when it does not.
Program.cs The entry point: the command line (–help and –version answered on the console with no window; the device commands an elevated restart resumes with; –after; –debug; in a DEBUG build, –debug-copy-delay), the debug log beside the program, whether the process is elevated, the one dialog font and warning-heading font every dialog is given, loading the engine before the main window opens, and the exit codes.
PropertiesForm.cs The Properties dialog for one entry of the image: its facts read-only (path, type, size, inode, links, times, a link’s target), and its mode, owner and group to change – the mode both as octal text and as a grid of permission boxes with the ls form beside them, the two kept in step; it validates on OK and hands the values back for the main window to apply.
PromptForm.cs The small dialog that asks for one line of text (a name, a hex file’s size, a Find text, a Go To offset), with OK and Cancel; the caller reads whether OK was pressed and what was typed once it closes. For a name the worker asks for, it also reports what is typed as the question’s draft, so a question an Exit hides comes back as it was.
ShellIcons.cs The Windows pane’s icons and type names, as Explorer shows them: asked of the Windows shell (by extension where one answer serves every file of a kind, by real path for folders and files with icons of their own), copied into the program’s own lists at whatever size View > Text Size sets; plus the shell’s icon for a menu item, This PC and the Downloads folder, and the shell’s own Properties window.

engine\

The engine, bifrost_engine.dll: BifrostFM’s own C at the top of the folder, compiled by build_engine.bat (gcc) together with the open-source code in the sub-folders into one 64-bit DLL in engine\out\.

File What it holds, and what for
bifrost_engine.h The engine’s public interface, the one header a caller includes: every exported function, status code, flag and structure, with the contract each call keeps – mirrored by hand in the program’s gui\EngineNative.cs and EngineSession.cs, and guarded by an API version the program checks when it loads the DLL.
bifrost_engine.c The engine’s core: opening and closing an image or device (with the system-disk guard and volume locks; a range with no ext2/3/4 filesystem tried as squashfs, by its magic, then as FAT or exFAT), flushing, browsing and the simple edits (make, remove, a tree removed entry by entry, rename, permissions, owner, times, links), and the internals every other engine file shares – the one-call-at-a-time gate (which keeps the ext-only calls off a FAT session), the error recorder, the path rules and their canonical form, and the directory reader.
bfe_device.c, bfe_device.h The raw I/O beneath everything: opening a file or a real disk or volume and telling which it is, its size, sector, disk number and model; sector-aligned reads and writes; which disk Windows runs from; and locking and dismounting a disk’s volumes before the disk is written.
bfe_blockdev.c, bfe_blockdev.h The block device lwext4, the filesystem check and FatFs read and write through, and squashfuse reads through: an image file or a real disk presented as 512-byte blocks, with a device’s sector alignment, the read-back that catches a card which does not keep its writes, and the read-only refusal.
bfe_fatio.c, bfe_fatio.h FatFs’s device layer: the five disk_* functions and the FAT timestamp FatFs asks for, written over the engine’s block device, so a FAT filesystem is read and written within its range with the same device, read-only and read-back rules as an ext4 one.
bfe_fat.c, bfe_fat.h The engine’s FAT side: a FAT12, FAT16, FAT32 or exFAT filesystem mounted through FatFs where no ext2/3/4 one is found, read-only or writable – the directory listing and one path’s facts (entries as files and directories with a made-up mode and FAT’s local time turned into UTC), the volume’s facts, the helpers for the writes FatFs has no single call for (a remove past the read-only attribute, a tree removed whole, a time set in local time), the engine’s one translation of a FatFs result into an errno, the letter-case fold FatFs matches names by, the largest file a volume holds, the unmount – and the making of a new FAT volume: its cluster size and label judged before anything is written, FatFs’s formatter over the range, the label written where FAT keeps it (the root’s entry and the boot sector’s field).
bfe_fs.c, bfe_fs.h The file calls the engine’s walks and edits make, written once for every kind of filesystem: open, read, write and close a file, remove, make and remove directories, rename, set a mode, an owner or a time, and read or make a link – each going to lwext4 on an ext2/3/4 session, to FatFs on a FAT one and to squashfuse on a squashfs one, every result in lwext4’s errno form, what FAT cannot hold (modes, owners, links) refused as unsupported, and every change on squashfs refused as read-only.
bfe_sqfs.c, bfe_sqfs.h The engine’s squashfs side: a squashfs 4.0 filesystem found by its magic where no ext2/3/4 one is, read through squashfuse, read-only only – the read squashfuse reads the image through (held inside the range, over the engine’s block device), the mount and unmount, the volume’s facts, one path’s facts (types from the inode’s type field, owners from the id table), a directory’s names, a link’s target and a file’s bytes.
bfe_internal.h What the engine’s own files share and export to nobody: the declarations of the core internals (bifrost_engine.c) and the text helpers (bfe_util.c), the shared constants, and the map of which function-name prefix belongs to which file.
bfe_util.c The text helpers every part of the engine uses: joining image and Windows paths, converting names between UTF-8 and UTF-16 (refusing malformed ones), and deciding whether an ext4 name can be a Windows file name.
build_engine.bat The engine’s build: every source of lwext4, the e2fsprogs pieces, the compression libraries, FatFs, squashfuse’s reader and the engine named one by one, compiled with gcc (the engine’s own files to its warning bar) and linked with the compiler’s runtime into one self-contained DLL.
bfe_capacity.c The capacity test: how much of a card really holds data – tagged test blocks written at sixty-four points across it, all written before any is read back, everything put back afterwards, and the boundary of a counterfeit card’s real size narrowed by halving.
bfe_resize.c Growing a filesystem to fill its partition or image – e2fsprogs’ resize2fs run inside the engine in place of its command-line front end, refusing a filesystem that has not been checked, and reporting progress as a check does.
bfe_fsck.c The filesystem check: e2fsprogs’ e2fsck run inside the engine in place of its command-line front end – report-only or repair, never a question asked – with its text and progress handed to the program as it goes, a fatal error returned instead of ending the process, and a repair whose writes a failing card did not keep reported as such.
bfe_fsck_io.c, bfe_fsck_io.h The bridge that lets the built-in e2fsck and resize2fs reach a disk: libext2fs’ I/O interface implemented over the engine’s own block device, so they read and write exactly the image, device or partition the engine has, with the same sector and read-only rules.
bfe_mkfs.c Making an empty filesystem – in a new image file of a chosen size, or in place over a partition of a card or disk, with the guards a device needs: ext2 / ext3 / ext4 with lwext4’s formatter, then putting right what it leaves wrong (free counts, reserved inodes, a real UUID, the root’s mode) so e2fsck accepts the result; FAT12/16, FAT32 or exFAT through bfe_fat.c.
bfe_copy.c The three recursive copies – image to Windows, Windows to image, and within the image – with the rules for what cannot cross to NTFS (Unix modes, owners, links, names Windows refuses), the plain-text metadata manifest that records it and restores it on the way back, conflicts, progress and cancel.
bfe_image.c Whole-device and raw-image work: a file’s or device’s facts, bounded raw reads and writes (how a partition table reaches the media), the dd-style raw copy between a device and an image file – with the system-disk, room and volume-lock guards, compressed sources, .xz output and the read-back verify – and the format and size of an image file.
bfe_rawbatch.c A partition table written as one operation: every piece of the table (MBR, GPT headers and entry arrays) checked first – range, sector grid, overlap, the open session’s own target, the system disk – then written under one open handle and, on a device, one holding of the disk’s volume locks, so Windows never sees the table half written.
bfe_compress.c, bfe_compress.h Compressed images: a streaming reader that recognises .xz, .gz, .zst and .zip by their first bytes, learns the image’s size where the format records it without decompressing, and hands back raw bytes in constant memory; and the multi-threaded .xz writer used when a device or image is saved compressed.
